# blotquant web

The Next.js front end: a gallery of measured cards, one card view, and a screen that analyses an
image you upload. Static export — `pnpm build` writes `out/`, which is the whole deployable.

## Running it

```
pnpm install
pnpm dev          # http://localhost:3000
pnpm lint         # eslint, --max-warnings 0
pnpm typecheck    # tsc --noEmit
pnpm test         # vitest run
pnpm build        # static export into out/
```

`pnpm build` reads `public/gallery/index.json` at build time, so the gallery must exist before
the site can be built. It is committed, so a fresh clone builds; rebuilding it is below.

## Building the gallery

The gallery is not generated by this package. Every card is a real measurement made by the
shipped API, so building it needs the API running:

```
# from the repository root, in one shell
python -m api --storage-root results/ --config-dir configs/

# in another
python -m tools.gallery.build
python -m tools.gallery.verdict_fixtures
```

`tools/gallery/build.py` posts each entry of `web/gallery.manifest.yaml` to `POST /analyze` and
writes `web/public/gallery/<id>/{result.json,display.json,display.png}` plus `index.json`. It
refuses to run if the API is not reachable and never starts it. `tools/gallery/verdict_fixtures.py`
then regenerates `web/test/fixtures/verdict/` — see "The verdict is computed twice" below. Run
both, in that order: the verdict fixtures embed the stored documents, so a rebuilt gallery leaves
them stale and `tests/test_gallery_verdict_fixtures.py` fails until they are regenerated.

`display.json` is the served `display` block with `png_base64` removed — the bytes are already
`display.png`. What remains is the labelling: `is_derivative`, `note` and `mapping`, which records
how many source DN one output level of the picture spans. The card page shows it in the provenance
panel, because a rendering of measured pixels shown next to a QC flag needs the block that says a
255 in the PNG is not evidence of saturation.

`web/gallery.manifest.yaml` implements the composition ruled on 2026-08-25 and recorded in
`docs/pr/phase-4b0.md`: six cards in the ruled order — blocked, flagged, detection beta, pass. Its
header records where each rectangle came from, and the two things a reader has to know: the two
flagged candidates the ruling rejected by name, and that `no_ratio_emitted` is not representable
from this corpus.

## `NEXT_PUBLIC_API_URL`

`lib/api.ts` posts to `process.env.NEXT_PUBLIC_API_URL ?? 'http://127.0.0.1:8000'`. Next inlines
`NEXT_PUBLIC_*` at build time, so this is a **build-time** setting, not a runtime one: a static
export talks to the URL it was built with, and pointing it somewhere else means rebuilding.

No `.env` file is committed. Set it in the shell or in the deploy's build environment:

```
NEXT_PUBLIC_API_URL=https://api.example.org pnpm build
```

## CORS — a real gap, not yet closed

**`api/app.py` installs no CORS middleware.** A page served from `localhost:3000` (or from any
deployed origin) that calls `http://127.0.0.1:8000` is therefore blocked by the browser's
same-origin policy, and the `/analyze` screen cannot work until that changes. The gallery is
unaffected: its cards are static files built ahead of time and are never fetched from the API.

This is recorded rather than routed around. There is no committed dev proxy in this package and
no CORS middleware was added to `api/` — enabling cross-origin access is a decision about who may
call the deployed service, which belongs with the API deployment. It is a **prerequisite of that
task**, and an open question: which origins, and whether the service should be same-origin with
the site instead, which would remove the question.

Until it is settled, the `/analyze` path can be exercised by serving the built site from the API's
own origin, or by running a proxy locally that is not committed here.

## The verdict is computed twice

`lib/verdict.ts` is a **mirror** of `api/display.py::lane_verdicts`, which is where the ruled
verdict mapping lives (`docs/PRE_REGISTRATION_2026-08-25_verdict_mapping.md`, Ruling 1). It is
duplicated because the API does not serve the verdict and the live `/analyze` path must show one
for a result that was never stored.

Two implementations of one ruled mapping diverge silently, so they are pinned to each other:

- `tools/gallery/verdict_fixtures.py` calls the **Python** function over every stored gallery
  document and over synthetic documents covering all three verdict classes, both blocked reasons
  and edge cases E1–E8, and writes `test/fixtures/verdict/`;
- `test/verdict.test.ts` asserts the TypeScript reproduces every fixture exactly, flag order
  included, and throws on every refusal fixture;
- `tests/test_gallery_verdict_fixtures.py` (Python) fails if the fixtures have drifted from
  `api/display.py`.

A fourth artefact records the divergences: `test/fixtures/verdict/divergences.json` is generated
by running the **Python** over a set of schema-invalid documents and recording what it actually did
with each, and `test/verdict.test.ts` asserts the TypeScript refuses every one. The file is the
record of how many there are; no count is repeated here, because the count that used to be was a
test's floor quoted as a census. The list used to be
prose in NOTES.md and was wrong three times; it is an observation now.

> **Gap: none of the TypeScript half runs in CI.** `.github/workflows/` has no Node step, so
> `vitest`, `eslint` and `tsc` are enforced by whoever remembers to run them. The Python↔fixture
> leg is enforced by `pytest`; the fixture↔TypeScript leg is not. Adding the job is an open item
> — see NOTES.md, "The web suite runs in no CI job".

Change the mapping in `api/display.py` first, regenerate, then follow it here. The mirror is debt;
it closes when the human rules on serving the verdict from the API. See NOTES.md,
"Phase 4b-web — the client-side verdict mirror".

## Layout

```
app/                  routes: / (gallery), /result/[id], /analyze
app/globals.css       the register's design tokens (@theme) and base layer
app/analyze/          the three steps, the lane editor and the refusal cards
app/analyze/lanes.ts  the lane list and the rules it is held to, pure and testable
components/ResultView.tsx  the result surface, rendered verbatim by /result/[id] and /analyze
components/RoiOverlay.tsx  the image with its ROI rectangles, exact at any rendered width
components/VerdictBadge.tsx  colour + glyph + word, the only way a verdict is shown
components/Measured.tsx      one number, carrying the JSON path it was read from
lib/result.ts         types mirroring schema/result.schema.json
lib/result-cells.ts   reading a document into table cells, each with its JSON path
lib/verdict.ts        the client-side mirror of the ruled verdict mapping
lib/verdict-display.ts  the one definition of colour + glyph + word per verdict
lib/verdict-sentence.ts the one sentence each verdict class gets, shared by both screens
lib/api.ts            the POST /analyze client and its typed refusals
lib/gallery.ts        build-time reads of public/gallery/ (never imported by a client component)
public/gallery/       committed build output of tools/gallery/build.py
test/fixtures/verdict/  committed output of tools/gallery/verdict_fixtures.py
test/fixtures/api/    refusal bodies captured verbatim from a running API
```

## Two limits of the `/analyze` screen

**It will not proceed with an image the browser cannot display.** No browser decodes TIFF; the
pipeline does. A lane editor that could not show the picture would be asking you to place
rectangles on a region you cannot see, so the screen says so and points at the CLI, which reads
the original.

**It does not check that lane rectangles do not overlap.** `pipeline/detect.py` refuses overlapping
caller ROIs and names both positions in the pair; the form checks only what it can check without
restating a pipeline rule, and shows the API's refusal verbatim. Nothing you type is ever silently
corrected: a rectangle past an edge stands as typed, with a message, and `Analyse` stays disabled.
