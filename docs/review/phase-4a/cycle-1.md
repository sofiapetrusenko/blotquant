## REQUIRED

**1. `pipeline/analyze.py:160` — an empty `lane_rois` silently turns detection back on, and the loud error written for that exact case can never fire.**
`supplied_lane_rois = tuple(lane_rois) if lane_rois else None` collapses `[]` into `None`. `pipeline/detect.py:282-287` raises `LaneRoiError("no lane ROI was supplied, but supplying lane ROIs is what switches lane detection off…")` for the same input. Two public functions in one call chain, opposite answers for one value. Because `analyze_image`, `pipeline/__main__.py:74` and `api/app.py:152` all normalise falsy→`None` first, that branch of `validate_lane_rois` is unreachable from every shipped entry point; it is a check that cannot fire, and its message describes behaviour the system does not have. This is a silent fallback in the CLAUDE.md sense, not an HTTP convention: on the HTTP side an absent `lane_roi` field arrives as `None`, never `[]`, so nothing about the request shape requires the collapse — it only bites the in-process caller. That caller is 4b: a UI that builds `lane_rois` from the user's rectangles and hands over an empty list when the user deletes the last one gets a full re-detection and a *different* set of numbers instead of the error the pipeline already wrote. Fix: `supplied_lane_rois = None if lane_rois is None else tuple(lane_rois)`, drop the `if lane_roi_specs else None` conditional in `api/app.py:152` in favour of an `is None` test, correct the `analyze_image` docstring (currently lines 138-142 assert the equivalence as a guarantee), and invert `tests/test_pipeline_lane_rois.py:231` (`test_an_empty_lane_roi_list_means_detection_runs`) to assert the raise.

**2. `api/display.py:96-103` — `DisplayDerivative.as_response_block` is dead in production, duplicates `api/app.py:114-121`, and is the only thing the envelope-shape test exercises.**
No production path calls it: `POST` calls `display.as_block()` and hands it to `_envelope`, which re-implements `{**block, "png_base64": b64encode(png)}` itself; `GET` cannot call it at all, since it holds a stored dict and PNG bytes rather than a `DisplayDerivative`. So the envelope's payload shape is defined in two places that nothing forces to agree — add a field in one and the other keeps shipping the old shape. Worse, `tests/test_api_display.py:101` (`test_the_response_block_carries_the_png_and_the_same_record`) reads as coverage of what the API returns but asserts only on the unused method. Delete `as_response_block` and that test, and re-point the assertion at `api.app._envelope`; then also fix `as_block`'s docstring at `api/display.py:76`, which currently says it was "Split out from :meth:`as_response_block`".

**3. `api/errors.py:71-75` — the justification for `NormalizationError` → 400 is false, and it routes internal defects to the caller as 4xx.**
The comment states "NormalizationError is raised only for a mistake in the *request* -- its own docstring enumerates them". The docstring does not: `pipeline/normalize.py` raises the same class at line 177 (a band carrying a QC flag outside the vocabulary), 306 (no total-protein signal for a detected lane), 396 (repeated band ids), 403 (repeated lane ids) and 413 (a band naming an undetected lane). Over HTTP every one of those inputs is produced by this service — band ids, lane ids, QC flags and the lane-integral map all come out of `analyze_image`, never off the wire. A duplicate band id is a detection defect that would be served as `400 {"error": "NormalizationError"}`, telling the caller to fix a request they got right. This is exactly the misclassification category 7 forbids in the opposite direction. Either split the internal-invariant raises in `pipeline/normalize.py` into a distinct class mapped to 500, or — if that is judged too large for 4a — narrow the comment to state which raise sites are caller-caused and record the known 4xx-for-internal-defect gap, rather than leaving a false claim as the mapping's stated basis.

**4. `api/app.py:99-111` — `_require_valid`'s message is factually wrong on the `GET` path, which is the path the code explicitly expects it on.**
The message says "the analysis produced a document that fails schema/result.schema.json … No caller input can cause this; it is a defect in this service". On `GET /results/{id}` no analysis ran; `get_result`'s own docstring (lines 249-251) names the real trigger — "a document written under an earlier contract". Since `RESULT_SCHEMA_VERSION` is a `const` and just went 1.1.0 → 1.2.0, every result stored by a previous build of this service now fails validation, and the operator is told to hunt a code defect when the actionable fact is "this stored result predates schema 1.2.0; re-analyse the image". Give `_require_valid` a caller-supplied context (or split the stored-document case) so the `GET` path reports the stale-contract cause and names the stored id and the two versions.

## SUGGESTED

- `tests/test_pipeline_lane_rois.py:163` proves bands are found inside a supplied lane but not that band detection is *unchanged*. The decisive version is a round trip: run `detect` without ROIs, feed its own lane rectangles back as `lane_rois`, and assert the `bands` tuple and the lane ROIs are identical and only `roi_source` differs. Cheap, and it pins the phase's first stated requirement.
- `api/display.py:92` ships `clipped_pixel_count: 0` as a literal — a measurement-shaped field that can only ever read zero, which is the objection this diff's own NOTES.md raises against a band `roi_source` that could only read `"detected"` (citing DEBT S17). Consider dropping it and keeping `clips: False`.
- The mapping block records `scales`/`clips` but not the quantization the module docstring is honest about: 16-bit values 65407-65535 all render as 255, so "255 in the PNG" is not "saturated". A `source_dn_per_output_level` field (or equivalent) would let the 4b trust feature avoid exactly the false inference the percentile-mode argument was written to prevent.
- `api/__main__.py` is 4a scope in my judgement (it is a dev server, explicitly defers deployment, adds no deploy config), but it is 55 lines with zero coverage while `pipeline/__main__.py` is tested end to end. A test on `build_parser` — both directories required, no defaults — would lock the property that makes it safe.
- `httpx` is test-only but sits in production `requirements.txt`. The inline comment justifies it; a `requirements-dev.txt` would be cleaner. Note `uvicorn` is imported only by `api/__main__.py`.
- `GET` re-validates the result document but returns `display.json` from disk unvalidated, and a corrupt `display.json` raises `JSONDecodeError`, which is not a `PipelineError` and so escapes the handler into Starlette's generic 500 (no traceback leaks to the client, but the response is not the JSON error shape the API otherwise promises).
- `api/app.py:229` does `image.file.read()` with no size cap, so upload size is bounded only by memory.
- FastAPI's own request-validation failures return 422 with `detail` as a *list*, colliding with the semantic 422 chosen for `DetectionError`/`BackgroundError` whose `detail` is a *string*. Worth documenting the `error` key as the discriminator.
- When lanes are caller-supplied, `provenance.parameters.detection.lane.*` is still echoed although lane detection did not run. `roi_source` makes it unambiguous, so this is not a false record — but a reader diffing two provenance blocks will see identical lane parameters for two runs where one of them applied none of them.
